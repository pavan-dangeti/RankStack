# ADR-0003 — No language model in the serving path

- Status: Accepted
- Date: 2026-10-08

## Context

RankStack must return a short explanation for each recommended item. The obvious implementation is
to call an LLM with the candidate list, the user's recent items and the model's feature
attributions, and ask for one sentence per item.

That would add 300–2000 ms to a request whose latency budget is 150 ms at p95, put an external API
(or a local multi-billion-parameter model) on the critical path of every request, and send
third-party catalogue and user-history content to a provider whose free tier may not exist on the
day of the demo.

The explanations also have a quality requirement: they must be *true* — traceable to why the model
scored an item, not plausible-sounding text.

## Decision

Explanations are generated by a deterministic, template-based layer, not by a language model.

1. Each explanation is a template chosen by which feature dominated the score for that item, filled
   with evidence the model actually used: the user's most recent interactions, the retrieved
   neighbour items, the category affinity, the text similarity source item.
2. The rendered explanation carries the evidence list in the API response, so any explanation can
   be traced back to a score and a feature. Example response field:
   `explanation: {template: "because_you_reviewed", evidence: [{item_id, reason, score_contribution}]}`.
3. The number of templates is small and fixed, and each one is unit-tested against a hand-computed
   expected string.
4. `LLM_API_KEY` configuration is accepted but unused by the serving code. The server module has no
   outbound HTTP client.

## Consequences

**Good.** p95 latency is unaffected by explanation cost. The demo cannot be broken by a provider
outage or quota. Explanations cannot hallucinate, and they cannot be manipulated by text in a
product title. No user or catalogue content leaves the process. Zero API cost.

**Bad.** Explanations are formulaic. For a demo that reads as templated rather than conversational,
which is a real aesthetic cost and the main argument against this decision.

**Risk.** A reviewer may read the explanations as shallow. The mitigation is that the *evidence* is
real — feature contributions from the ranker and actual retrieved neighbours — so the explanation
says something true that the model did in fact use, which is a stronger claim than fluency.

## Alternatives considered

- **LLM-generated explanations at request time** — rejected: latency, cost, quota, privacy and
  hallucination risk, all at once.
- **Pre-generated explanations stored per item** — rejected: an explanation must depend on the user,
  not only the item.
- **Local small LLM (1–3B) on the serving host** — rejected: does not fit the free hosting memory
  budget alongside the index, and adds p99 variance for no accuracy gain on a templated task.
- **Keep templates, offer an optional offline LLM narrative in the demo UI only** — deferred: could
  be added later as a clearly non-critical decoration, never on the API path.
